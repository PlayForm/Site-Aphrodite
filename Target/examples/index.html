I // THE THRESHOLD TUNING WALKTHROUGH

Four knobs, hot

The four hot-reload thresholds are the only compression values the running proxy re-reads: tool_threshold_token, tool_threshold_cache, inline_threshold and code_multiplier.

Edit + save, or POST /reload - the new values apply immediately, with no restart (README.md:389-391).

Everything else about a proxy is fixed at startup.

The mechanics of the hot path: the config-file watcher reacts to Modify events on aphrodite.toml with a 500 ms debounce, reloads the file, and stores the four resolved thresholds into every live AppState's atomics - nothing else is updated live (docs/architecture/07-config-resolution.md:71).

The dylib session is a different story: it re-applies config fields on change only when auto_reload = true (README.md:390-391).

THE COMMAND

POST /reload

THE OUTPUT

SAME BYTES ON THE CACHE LANE: NO PREVIEW, NO MARKER, NO STORE ENTRY

THE MARKER

II // THE RETRIEVAL ROUND-TRIP

Compress, marker, retrieve, byte-exact

The lifecycle of one payload: the hook hashed it (BLAKE3), stored the bytes in the session store, and replaced the output with a {"<<>>"} marker plus a preview.

The transcript then carried the marker instead of the content - hash, type, size, ~15 tokens.

When the next action needs the substance, the agent calls aphrodite_retrieve with the hash - or pastes the marker body directly; every retrieval entry point accepts it, suffix or no suffix.

What comes back is the original content byte-for-byte, nested markers resolved recursively (docs/ccr/marker-format.md).

The caveat, printed on the tool's own contract: markers stay resolvable for the life of the session but do not survive a session restart - the dylib is loaded once per process, so a new session starts a fresh store (docs/tool-relay/tools.md:36-39).

The proxy's token listener backs its store with SQLite, which is the durability escape from that rule.

THE COMMAND

APHRODITE_RETRIEVE(HASH)

THE OUTPUT

III // THE CHAIN-SPLIT

One command, many markers

Chain-split is a Hermes plugin-side feature, not a proxy one: with it enabled, pre_tool_call rewrites a chained shell command by echoing segment markers, and transform_terminal_output splits the produced output into per-segment pieces - the hook compresses each segment into its own marker, so the model sees several compact previews instead of one large blob (docs/proxy/compression.md:366-379).

It is opt-in: chain_split = false by default, because invisible segment markers pollute redirected stdout.

The split floor and cap are chain_split_min_segments = 2 and chain_split_max_segments = 6.

The split is unconditional once marked - segment compression happens before the threshold gate, so marked output never leaks raw.

And it is careful: constructs that would corrupt control flow (heredocs, loops spanning segments) are left untouched.

The proxy never performs chain splitting - it only sees Chat Completions responses.

THE COMMAND

cd project && cargo build --release && cargo test 2>&1

THE OUTPUT

PER-SEGMENT MARKERS BEHIND IT - EACH SEGMENT ITS OWN RECEIPT:
<<<CCR:f8a1d4c7...b0e3|build_output|210>>>
<<<CCR:a9b2c5d8...e1f4|test|188>>>

THE MARKER

PREVIEW + HASH
[chain:3 | build ...]
<<<CCR:e7c0f3a6...c1f4|terminal|398>>>

OFF BY DEFAULT · Without the split, the same compound command is one terminal blob with one marker; the build preview and the test preview never separate.

IV // THE DIRECTIVES IN ACTION

Seven built-ins, one budget

Short behavioral .md files, baked into the binary and materialized on plugin registration, injected verbatim every pre_llm_call - they teach retrieval vocabulary, never the compression mechanism.

The discovery order is strictly first-wins, never merged: APHRODITE_DIRECTIVES_DIR → ./directives/ → ~/.hermes/aphrodite/directives/ → binary-relative.

Any .md file in a discovered directory becomes a directive named after its stem - the built-ins are not special-cased (docs/plugin/directives.md:51-58).

The budget math: 2,000 characters per directive body, 4,000 characters across all active directives combined - and the whole per-turn injection (directives + nudges + recall catalog + retrieve hint) lives under one hard cap, flow_budget_chars, default 4,000 (shipped example: 2,600).

Sections drop from the bottom when over budget; directives and nudges never drop.

THE COMMAND

aphrodite_directive("swap", "explore")

THE OUTPUT

THE ASSEMBLED TURN // pre_llm_call
[directives: name1, name2]
focus: targeted execution, marker-aware retrieval
[nudge: ...]
[recall] catalog summary

THE MARKER

V // THE TOOL-RELAY CALLBACK

Synchronous, unless you say otherwise

POST /tool/relay runs the tool synchronously unless the request carries a callback_url - then the call becomes asynchronous: the proxy answers immediately with {"{success: true, async_call: true}"}, executes the tool, and POSTs the real result to the callback URL later (docs/tool-relay/callbacks.md:29-48).

The guardrails are strict.

The callback URL must be https-only - http, including loopback, and any other scheme are rejected with HTTP 400 before anything executes (SSRF protection).

The delivery is a 5-second, fire-and-forget POST: no auth header, no retries, the outcome untracked (only relay calls themselves are counted in /stats).

Only aphrodite_retrieve, aphrodite_compress and aphrodite_list are relayable; anything else is an error.

On graceful shutdown the task tracker waits for in-flight deliveries, so none are lost mid-flight.

THE COMMAND

POST /tool/relay

THE OUTPUT

SYNCHRONOUS // NO CALLBACK_URL
POST /tool/relay - tool runs - full result inline
ASYNC // WITH CALLBACK_URL
{"{ \"success\": true, \"result\": null, \"async_call\": true }"}
... later, 5s timeout, no auth, no retries ...
POST callback_url - the real result

THE MARKER

PREVIEW + HASH
compact metadata: hash, type, size, marker
none - a relay result stays raw through the hook pipeline.

Compressing an aphrodite_retrieve result would replace resolved content with another marker, which is why the result itself is compact metadata and never absorbed.

VI // THE ESSENTIAL-TOOL SKIP GATE

What stays raw, and why

Before any classification or storage, transform_tool_result runs its skip gates: a result is left untouched when it is empty; when the tool is in the essential set - skill_view, skills_list, skill_manage, memory, session_search, read_file, read_terminal; when it is one of Aphrodite's own tools or a headroom helper; or when it sits below the tool threshold (docs/plugin/hooks.md:76-83).

The logic is not protectionism - it is information theory per surface.

The essential tools return compact, self-describing metadata the agent needs raw: a skill's instructions, a memory entry, a file's content.

Compressing them would trade precision for nothing.

The self-tools are already the compressed form: their output is a marker or a catalog, and marking a marker is the preview-doubling bug in slow motion.

And the size gate is the quiet one - most tool output is simply small, and passes through without a store entry ever existing.

One subtlety: the hook tracks file references before the skip gates, so read_file and search_files results feed the recall catalog even when it never compresses them (docs/plugin/hooks.md:92-94).

THE COMMAND

read_file

THE OUTPUT

01 EMPTY · nothing to compress
02 ESSENTIAL SET · the agent needs raw output
03 SELF TOOLS · already compact metadata
04 SIZE GATE · 1,024 bytes on the token lane, 8,192 on the cache lane; 0 disables the gate

THE MARKER

PREVIEW + HASH
the raw bytes, unchanged
none - this is the gate that refuses the machine.

The gate order is fixed: the empty check, the essential set, the self-tools, then the size gate (docs/plugin/hooks.md:69-94).

VII // THE DUAL-LISTENER PARALLEL

Same output, two lanes, one marker

A single binary can run two listeners with different roles - the cache proxy on :9797 (in-memory DashMap, 10,000 entries, 8192-byte threshold) and the token proxy on :9798 (SQLite at ccr.db, 1024-byte threshold, persistent, tool-relay-capable).

Each has its own AppState and CCR backend; both bind to loopback by default (docs/proxy/architecture.md:9-35).

The parallel that matters: the same payload crosses the plugin-hook lane (the hook intercepts it at the tool boundary, no API round-trip) and the proxy lane (the proxy compresses Chat Completions responses in flight) - and the marker it becomes is byte-identical across the two paths, as are the enriched previews (CHANGELOG.md:616-617).

The preview-doubling regression of v1.3.4 was caught precisely because the two paths were held to that standard.

THE COMMAND
