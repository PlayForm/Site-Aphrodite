THE WORKED SCENARIOS // HOW IT ACTUALLY MOVES

Seven scenarios,
one lifecycle

Not what the output looks like - what happens to it, step by step. A threshold edit propagates through a running proxy. A marker travels from compression to byte-exact retrieval. A compound command splits into segments. Directives assemble under a budget. A relay call fires a callback. Essential tools refuse the machine. And the same payload crosses two listeners without changing shape.

I // THE THRESHOLD TUNING WALKTHROUGH

Four knobs, hot

The four hot-reload thresholds are the only compression values the running proxy re-reads: tool_threshold_token, tool_threshold_cache, inline_threshold and code_multiplier. Edit + save, or POST /reload - the new values apply immediately, with no restart (README.md:389-391). Everything else about a proxy is fixed at startup.

The mechanics of the hot path: the config-file watcher reacts to Modify events on aphrodite.toml with a 500 ms debounce, reloads the file, and stores the four resolved thresholds into every live AppState's atomics - nothing else is updated live (docs/architecture/07-config-resolution.md:71). The dylib session is a different story: it re-applies config fields on change only when auto_reload = true (README.md:390-391).

II // THE RETRIEVAL ROUND-TRIP

Compress, marker, retrieve, byte-exact

The lifecycle of one payload: the hook hashes it (BLAKE3), stores the bytes in the session store, and replaces the output with a <<<CCR:hash|type|size>>> marker plus a preview. The transcript now carries the marker instead of the content - hash, type, size, ~15 tokens.

When the next action needs the substance, the agent calls aphrodite_retrieve with the hash - or pastes the marker body directly; every retrieval entry point accepts it, suffix or no suffix. What comes back is the original content byte-for-byte, nested markers resolved recursively (docs/ccr/marker-format.md).

The caveat, printed on the tool's own contract: markers stay resolvable for the life of the session but do not survive a session restart - the dylib is loaded once per process, so a new session starts a fresh store (docs/tool-relay/tools.md:36-39). The proxy's token listener backs its store with SQLite, which is the durability escape from that rule.

III // THE CHAIN-SPLIT

One command, many markers

Chain-split is a Hermes plugin-side feature, not a proxy one: with it enabled, pre_tool_call rewrites a chained shell command by echoing segment markers, and transform_terminal_output splits the produced output into per-segment pieces - each segment compressed into its own marker, so the model sees several compact previews instead of one large blob (docs/proxy/compression.md:366-379).

It is opt-in: chain_split = false by default, because invisible segment markers pollute redirected stdout. The split floor and cap are chain_split_min_segments = 2 and chain_split_max_segments = 6. The split is unconditional once marked - segment compression happens before the threshold gate, so marked output never leaks raw. And it is careful: constructs that would corrupt control flow (heredocs, loops spanning segments) are left untouched. The proxy never performs chain splitting - it only sees Chat Completions responses.

THE STREAM // CHAIN_SPLIT = TRUE
cd project && cargo build --release && cargo test 2>&1
[chain:3 | build ...]
<<<CCR:e7c0f3a6...c1f4|terminal|398>>>
PER-SEGMENT MARKERS BEHIND IT - EACH SEGMENT ITS OWN RECEIPT:
<<<CCR:f8a1d4c7...b0e3|build_output|210>>>
<<<CCR:a9b2c5d8...e1f4|test|188>>>
OFF BY DEFAULT · Without the split, the same compound command is one terminal blob with one marker; the build preview and the test preview never separate.

IV // THE DIRECTIVES IN ACTION

Seven built-ins, one budget

Short behavioral .md files, baked into the binary and materialized on plugin registration, injected verbatim every pre_llm_call - they teach retrieval vocabulary, never the compression mechanism. The discovery order is strictly first-wins, never merged: APHRODITE_DIRECTIVES_DIR → ./directives/ → ~/.hermes/aphrodite/directives/ → binary-relative. Any .md file in a discovered directory becomes a directive named after its stem - the built-ins are not special-cased (docs/plugin/directives.md:51-58).

The budget math: 2,000 characters per directive body, 4,000 characters across all active directives combined - and the whole per-turn injection (directives + nudges + recall catalog + retrieve hint) lives under one hard cap, flow_budget_chars, default 4,000 (shipped example: 2,600). Sections drop from the bottom when over budget; directives and nudges never drop.

aphrodite_directive("swap", "explore") - no config edit, takes effect on the very next turn. The active set is per-process state: it persists across a session reset.
THE BUILT-IN SET // SEVEN, BAKED IN

ccr-handling how to read the marker and when to retrieve vs. skip

explore broad context, aggressive prefetch, resolve what matters
lazy only what this turn strictly requires; defer the rest
lazy-eval markers accumulate across turns; you decide when to resolve

V // THE TOOL-RELAY CALLBACK

Synchronous, unless you say otherwise

POST /tool/relay runs the tool synchronously unless the request carries a callback_url - then the call becomes asynchronous: the proxy answers immediately with {success: true, async_call: true}, executes the tool, and POSTs the real result to the callback URL later (docs/tool-relay/callbacks.md:29-48).

The guardrails are strict. The callback URL must be https-only - http, including loopback, and any other scheme are rejected with HTTP 400 before anything executes (SSRF protection). The delivery is a 5-second, fire-and-forget POST: no auth header, no retries, the outcome untracked (only relay calls themselves are counted in /stats). Only aphrodite_retrieve, aphrodite_compress and aphrodite_list are relayable; anything else is an error. On graceful shutdown the task tracker waits for in-flight deliveries, so none are lost mid-flight.

THE TWO LANES OF ONE RELAY CALL
SYNCHRONOUS // NO CALLBACK_URL
POST /tool/relay - tool runs - full result inline
ASYNC // WITH CALLBACK_URL
{ "success": true, "result": null, "async_call": true }
... later, 5s timeout, no auth, no retries ...
POST callback_url - the real result

VI // THE ESSENTIAL-TOOL SKIP GATE

What stays raw, and why

Before any classification or storage, transform_tool_result runs its skip gates: a result is left untouched when it is empty; when the tool is in the essential set - skill_view, skills_list, skill_manage, memory, session_search, read_file, read_terminal; when it is one of Aphrodite's own tools or a headroom helper; or when it sits below the tool threshold (docs/plugin/hooks.md:76-83).

The logic is not protectionism - it is information theory per surface. The essential tools return compact, self-describing metadata the agent needs raw: a skill's instructions, a memory entry, a file's content. Compressing them would trade precision for nothing. The self-tools are already the compressed form: their output is a marker or a catalog, and marking a marker is the preview-doubling bug in slow motion. And the size gate is the quiet one - most tool output is simply small, and passes through without a store entry ever existing.

One subtlety: file references are tracked before the skip gates, so read_file and search_files results feed the recall catalog even when they are never compressed (docs/plugin/hooks.md:92-94).

THE GATES // IN ORDER
01 EMPTY nothing to compress
02 ESSENTIAL SET the agent needs raw output
03 SELF TOOLS already compact metadata
04 SIZE GATE 4,096 chars default; 0 disables the gate

VII // THE DUAL-LISTENER PARALLEL

Same output, two lanes, one marker

A single binary can run two listeners with different roles - the cache proxy on :9797 (in-memory DashMap, 10,000 entries, 8192-byte threshold) and the token proxy on :9798 (SQLite at ccr.db, 1024-byte threshold, persistent, tool-relay-capable). Each has its own AppState and CCR backend; both bind to loopback by default (docs/proxy/architecture.md:9-35).

The parallel that matters: the same payload crosses the plugin-hook lane (intercepted directly at the tool boundary, no API round-trip) and the proxy lane (Chat Completions responses compressed in flight) - and the marker it becomes is byte-identical across the two paths, as are the enriched previews (CHANGELOG.md:616-617). The preview-doubling regression of v1.3.4 was caught precisely because the two paths were held to that standard.

VIII // THE TURN CYCLE, INTERACTIVE

The scenarios above each zoom into one mechanism. This is the loop that holds them: the six hooks, in firing order, with what the agent sees and what the system does at each step.

THE TURN CYCLE // SIX HOOKS, ONE LOOP
01 / 06
AGENT-VIEW
a clean slate - nothing injected yet
the call may be rewritten before it runs
a large result comes back as a preview and a marker
same treatment for command output - chain split first
the turn opens with directives, nudges, and the recall catalog
the answer arrives - the machinery tidies up
SYSTEM-PATH
on_session_start resets every piece of per-session state: turn counter, conversation index, recent markers, referenced files, tool-event telemetry, ephemeral directives. It injects nothing; the orientation renders on the first pre_llm_call.
pre_tool_call can auto-background long-running terminal/process calls (poll worker, default on) and split chained commands (chain split, off by default). If neither applies, the call passes through unchanged.
transform_tool_result runs telemetry, file-reference tracking, the skip gates, classification, the EMA-tuned threshold, then the BLAKE3 store and the swap.
transform_terminal_output mirrors the tool pipeline: telemetry, per-segment chain split before the threshold gate, the 1,024-character gate, classify, store, swap.
pre_llm_call runs the poll-worker checkpoint, then the assembler composes the injection under one 4,000-character budget, dropping sections from the bottom - recall first to go; directives and nudges never drop.
post_llm_call archives the last marker into the conversation index, advances the turn counter, purges expired nudges (after the counter advances, so a one-shot renders exactly once), and expires stale poll-worker tasks. Then the next turn begins.

IX // ONE RUNTIME HOME, INTERACTIVE

The history behind issue #40, as a decision walk: how the runtime home is resolved today, and why both halves of the plugin agree by construction.

THE HOME DECISION // RESOLVED ONCE, SHARED BY BOTH HALVES
01 / 05
AGENT-VIEW
you set APHRODITE_HOME - the whole stack obeys
per-Hermes-home isolation, extended to the Rust half
upgrades keep working - with a warning, never a migration
the startup log tells you which home was chosen and why
a non-default HERMES_HOME with no install reports 'not installed'
SYSTEM-PATH
the shim resolves the runtime home once at register() and exports it to the Rust half through APHRODITE_HOME + APHRODITE_DIRECTIVES_DIR, so the dylib and the spawned proxy binary agree by construction.
no override: the home derives from the Hermes home (HERMES_HOME), honored with the same precedence on the Rust side through the shared home module.
when the Hermes-home-derived home holds no install but the pre-2.2 ~/.hermes/aphrodite does, the legacy home is adopted with a one-line warning. Adoption never fires for throwaway homes (probe scratch, temp homes), preserving the catalog probe's isolation.
the startup log prints: runtime home: path (decided by ...). Before v1.6.3, the shim read HERMES_HOME while the Rust half read HOME - the divergence that orphaned configs and disabled plugins whenever the two differed. Fixed as one decision, shared.
the catalog review dropped the legacy ~/.hermes/aphrodite adoption from _runtime_home(): a non-default HERMES_HOME with no install no longer quietly shares one runtime home across profiles.
