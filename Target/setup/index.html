SETUP

Install Aphrodite

A tool call's output becomes part of the model's context, so Aphrodite is installed where that output is produced.

Aphrodite is installed as a Hermes Agent plugin (recommended) or run as a standalone proxy for OpenAI-compatible APIs.

Two things to know first: the plugin never downloads anything on its own - you run one setup command, and it fetches the Aphrodite binary and library from GitHub Releases, verifies them with SHA-256, and stores them in ~/.hermes/aphrodite/. And you need no Rust toolchain for the two plugin routes: the catalog and the clone install prebuilt binaries. The Cargo and from-source routes do build with Rust, and need 1.88+.

Not sure which to choose? Use the plugin catalog (Option 1).

01 // POSITIONING // INSTALL // FOUR ROUTES

Which route to take

Four routes, one engine. They differ in what they fetch and who owns the files afterwards - and in how much of the plugin you get: Cargo installs the proxy and a hooks-only loader, not the plugin tree. What Aphrodite does once the full plugin is running is the same on all four.

NO RUST FOR #1-#2 RUST 1.88+ FOR #3-#4 SHA-256 VERIFIED

The full host map, including the flavors still planned, is laid out on FLAVORS .

The four routes follow in full, command by command.

03 // OPERATIONAL WORKFLOW // THE TRANSCRIPT // ROUTE BY ROUTE

Four installs, one at a time

Each route is self-contained: the commands, what they leave on disk, what makes them fail, and the one check that says the install is live. The recommended path is selected first; the other three are one pill away, in the same container.

Platform is an input, not a footnote. Every route ships two complete lanes - directory creation, discovery and linking, download, enable, verification - and every command block carries the shell it is written for. A Windows lane contains no POSIX command, and a macOS / Linux lane contains no PowerShell.

WINDOWS: use PowerShell and run pwsh ./download.ps1 instead of bash download.sh - the full Windows walkthrough is on /docs/install/windows/ .

Plugin catalog install

#1 // PLUGIN CATALOG 5 STEPS READY
  1. 01

    Install the plugin from the catalog

    hermes plugins install aphrodite

    Checks out the catalog entry's reviewed, pinned commit - never a branch tip. Hermes asks Enable now? at the end of this step; the next step answers it explicitly, so the sequence does not depend on a prompt.

    EXPECT A pinned checkout in ~/.hermes/plugins/aphrodite - plugin.yaml plus the __init__.py shim.

  2. 02

    Enable the plugin

    BEFORE hermes on PATH.

    hermes plugins enable aphrodite

    Or answer yes at the Enable now? prompt - this is the same write, run as its own step so it can be re-run on its own.

    hermes plugins enable aphrodite skipped: enabling is a separate write to Hermes's own config.yaml, so a finished install alone does not register the hooks.

  3. 03

    Step into the installed plugin folder

    cd ~/.hermes/plugins/aphrodite

    download.sh is a file in the plugin tree, not a command on PATH, so the next step has to run from inside the folder.

    A download.sh run from outside the plugin folder: the script is a file in the tree, so cd into it before running it.

  4. 04

    Fetch the prebuilt binary and library

    bash download.sh

    Fetches the prebuilt binary and dylib from GitHub Releases into ~/.hermes/aphrodite/binaries/ - never into the plugin directory - validated against the in-tree SHA256SUMS.txt and magic-byte checked. Nothing is compiled and no Rust toolchain is required. Pin both explicitly: bash download.sh 1.6.5 x86_64-unknown-linux-gnu.

    EXPECT aphrodite + libaphrodite_hermes in ~/.hermes/aphrodite/binaries/.

    No route to GitHub Releases: the fetch step fails. The plugin is already enabled in config.yaml by step 2, so Hermes tries to load it - and a loader with no binary logs the setup command and stays inert until the binary is present. An enabled configuration is not a runtime that can load; register() never downloads anything on its own.

    A checksum that does not match SHA256SUMS.txt: the verify step fails, and the honest fix is a re-run, not a hand-copied file.

  5. 05

    Start Hermes

    hermes

    The plugin launches the proxy pair from the binaries you just fetched: :9797 (cache) and :9798 (token).

    EXPECT A log line saying Aphrodite is enabled, then two proxy listeners.

Crates.io install

#3 // CARGO 3 STEPS READY
  1. 01

    Install the proxy binary

    cargo install aphrodite

    Built from crates.io on your machine, so this route does need a Rust toolchain: 1.88+, and the repo's own toolchain pins nightly.

  2. 02

    Install the plugin's dylib and helper bin

    cargo install aphrodite-hermes

    The native library the Python loader loads, plus the helper binary.

  3. 03

    Run setup

    BEFORE hermes on PATH; Rust 1.88+.

    aphrodite setup

    Provisions ~/.hermes/aphrodite/ - the binary, the dylibs, aphrodite.toml from the embedded template and the BINARY_VERSION pin - then writes the hooks-only loader, plugin.yaml + __init__.py, into ~/.hermes/plugins/aphrodite/, removing a stale symlink from older installs first. It ends by running hermes plugins enable aphrodite.

    EXPECT The runtime home provisioned, the loader written, the plugin registered.

    No hermes on PATH: step one runs hermes --version and fails fast with a clear error, before anything is written.

    A missing libaphrodite_hermes aborts setup; a missing core libaphrodite only warns - the plugin loads the Hermes dylib, not the core one.

    An existing aphrodite.toml is left alone unless you pass --force; --cache-port and --token-port move the pair off 9797/9798 for a second agent on the same machine.

    A failed hermes plugins enable: setup prints a warning and carries on - the binaries are installed, the registration is not.

MACOS GATEKEEPER

Every artifact copy in aphrodite setup goes through one Gatekeeper-safe path: ditto (metadata-preserving), falling back to fs::copy + xattr -c to clear quarantine, then install_name_tool -id @rpath/<name> and an explicit ad-hoc codesign -f -s - for dylibs. A machine missing Xcode Command Line Tools used to get a SIGKILLed binary with zero diagnostic; every step now prints a specific warning instead.

04 // PERSISTENCE ARCHITECTURE // AFTER ANY ROUTE // THE LAYOUT

What changes on disk

THE LAYOUT
~/.hermes/
├── plugins/
│   └── aphrodite/          ← hooks-only: plugin.yaml + __init__.py loader
└── aphrodite/              ← canonical runtime home
    ├── aphrodite.toml      ← proxy/engine config (written by aphrodite setup)
    ├── BINARY_VERSION      ← binary version pin
    ├── binaries/
    │   ├── aphrodite       ← proxy binary
    │   └── libaphrodite_hermes.dylib   ← dylib the plugin loads
    ├── ccr.db              ← SQLite CCR store (created on first run)
    ├── directives/         ← active directive files
    └── logs/               ← proxy/engine logs

All four routes converge on the same two directories. Nothing else moves: no PATH edit, no shell profile, no system-wide install.

THE PLUGIN DIRECTORY

The plugin directory stays hooks-only: it carries just plugin.yaml and the __init__.py loader that registers hooks and tools, and the plugin never writes, downloads or modifies anything inside it.

THE RUNTIME HOME

Every runtime artifact lives in ~/.hermes/aphrodite/ : binaries, config, directives, the CCR database and logs. That split is what lets the catalog own the checkout while the binaries live somewhere else entirely.

On plugin startup layout_check.py checks toward this schema; installed layouts are already canonical, because aphrodite setup produced them.

8 STEPS WHAT APHRODITE SETUP DOES, IN ORDER + −
  1. Verifies hermes is on PATH (hermes --version) - fails fast with a clear error if not.
  2. Creates the runtime home: ~/.hermes/aphrodite/ and ~/.hermes/aphrodite/binaries/.
  3. Copies the binary into binaries/ with locked-down permissions - macOS copies go through the Gatekeeper-safe path above.
  4. Locates libaphrodite_hermes (and the optional core libaphrodite): local build and install dirs first, then the matching GitHub release with SHA-256 verification. A missing libaphrodite_hermes aborts setup; a missing core dylib only warns.
  5. Writes aphrodite.toml from an embedded template (--cache-port / --token-port, defaults 9797/9798) - only if none exists, unless you pass --force.
  6. Writes the hooks-only loader into ~/.hermes/plugins/aphrodite/: plugin.yaml + the __init__.py shim, always refreshed on re-run; a stale symlink from older installs is removed first.
  7. Writes the BINARY_VERSION pin into the runtime home.
  8. Runs hermes plugins enable aphrodite - a failed registration prints a warning, it does not abort.

05 // CONFIGURATION // /CONFIG.TOML

Configuration

Two files matter and they share no keys: aphrodite.toml for everything that tunes how Aphrodite compresses, and Hermes's own config.yaml for enabling the plugin.

# resolution order:
./aphrodite.toml then ~/.hermes/aphrodite/aphrodite.toml
# precedence:
env var > TOML > default

[compression]
auto_reload = false # opt-in

[flow]
budget_chars = 2600 # hard cap per turn
TEMPLATES IN THE REPO: aphrodite.toml.example + the embedded template

Two shipped files stay in sync: aphrodite.toml.example (the annotated reference) and the embedded template the binary ships with.

Keys not yet wired into the runtime are annotated DOCUMENTED BUT UNWIRED in the example - it is the source of truth for the documented surface.

TWO PARSERS, ONE FILE

The Rust HTTP proxy ( config/proxy.rs ) reads [[proxies]] ,[defaults] , the four hot-reload thresholds plus auto_expand / auto_expand_limit / max_request_body_size, and preview_max_chars. The Hermes dylib session ( config_loader.rs ) reads the [compression] engine keys, [defaults] model/api_url, [flow], [directives] ,[prompts] and [templates] .

NOT HERMES'S CONFIG.YAML

The only Aphrodite-relevant keys in config.yaml are plugins.enabled: [aphrodite] , added by hermes plugins enable , and optionally context.engine: aphrodite with its threshold. Ports, thresholds, preview style and prompt wording all belong in the toml.

Every knob the file exposes is explorable on /config/ , and the complete schema is /docs/config/aphrodite-toml/ .

Every install failure announces itself in one of six ways. The proxy's own stderr goes to ~/.hermes/aphrodite/proxy-stderr.log - read that file before anything else.

07 // PROXY // THE STANDALONE LANE

Run it without Hermes

The same compression engine runs as a standalone proxy: point any OpenAI-compatible client's base_url at http://localhost:9798 (token) or :9797 (cache), and responses compress over plain HTTP.

Invoked without an aphrodite.toml, the binary needs --api-key or APHRODITE_API_KEY. That is a startup requirement, not an upstream call - a placeholder is enough to prove the binary serves.

PORTMODEWHAT IT SERVES
9797cachethe cache proxy - threshold 2048 bytes by default
9798tokenthe token proxy - threshold 256 bytes by default

START // the binary, no Hermes

./aphrodite --api-key «redacted:sk-...» --listen 127.0.0.1:9798

The key is redacted here on purpose: a placeholder is enough, because the flag is a startup requirement rather than a credential the binary verifies.

CHECK // the health endpoint

curl http://127.0.0.1:9798/health

EXPECT // the health body

{"status":"healthy","ccr":true,"mode":"token","version":"<current version>","fill_pct":...}
aphrodite: no API key configured - set APHRODITE_API_KEY env var or api_key in aphrodite.toml STDERR
No aphrodite.toml in the working directory - the CLI mode has no config to read a key from, so the flag (or the env var) is the whole requirement.
REVEALED

You do not need a real Hermes session, a real Hermes install or a real upstream API key to confirm the binary itself works: starting the proxy and hitting /health never calls upstream. Set APHRODITE_NO_AUTO_LAUNCH=1 if you launch it yourself and do not want the plugin to start a second pair - there is no auto_start key in either config file.

The full surface is documented on the proxy pages: architecture , compression , handlers , retry .

08 // UNINSTALL // THREE COMMANDS AND A DIRECTORY

Uninstall

Disable the plugin, remove the loader, then stop anything still running. Every command is its own copy control, so a reader never pastes the sentence about the command.

BASH - macOS / Linux
  1. 01 Disable the plugin
    hermes plugins disable aphrodite
  2. 02 Remove the loader
    rm -rf ~/.hermes/plugins/aphrodite
  3. 03 Stop anything still running
    pkill -f "aphrodite" 2>/dev/null || true
POWERSHELL - Windows
  1. 01 Disable the plugin
    hermes plugins disable aphrodite
  2. 02 Remove the loader
    Remove-Item "$env:USERPROFILE\.hermes\plugins\aphrodite" -Recurse
  3. 03 Stop anything still running
    Get-Process aphrodite -ErrorAction SilentlyContinue | Stop-Process

Remove ~/.hermes/aphrodite/ as well to clean up the binaries, config, CCR database and logs the download scripts or aphrodite setup wrote.

On Windows the runtime home is %USERPROFILE%\.hermes\aphrodite\ .
