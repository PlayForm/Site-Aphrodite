SETUP

Install Aphrodite

Aphrodite is installed as a Hermes Agent plugin (recommended) or run as a standalone proxy for OpenAI-compatible APIs.

Two things to know first: the plugin never downloads anything on its own - you run one setup command, and it fetches the Aphrodite binary and library from GitHub Releases, verifies them with SHA-256, and stores them in ~/.hermes/aphrodite/. And you do not need Rust unless you build from source.

Not sure which to choose? Use the plugin catalog (Option 1).

INSTALL // FOUR ROUTES
NO RUST FOR #1-#2 RUST 1.88+ FOR #3-#4 SHA-256 VERIFIED

Which route to take

Four routes, one engine. They differ in what they fetch and who owns the files afterwards - never in what Aphrodite does once it runs.

ROUTEWHAT IT INSTALLSNEEDS RUSTUSE IT WHEN
1 // PLUGIN CATALOGthe pinned checkout, then the binariesnoyou want the reviewed commit the catalog pins
2 // GIT CLONEthe plugin, linked into ~/.hermesnoyou want the plugin tree in your own checkout
3 // CARGOthe binaries, then a minimal loaderyesyou only need the proxy, or want cargo to own the versions
4 // FROM SOURCEa local release build you point the plugin atyesyou are changing the code, not only running it

The full host map, including the flavors still planned, is laid out on FLAVORS.

The transcript below is the same four routes in full, command by command.

WINDOWS: use PowerShell and run pwsh ./download.ps1 instead of bash download.sh - the full Windows walkthrough is on /docs/install/windows/.

CHOOSE BY INTENT
  • One command and the reviewed commit: #1.
  • The plugin tree in your own checkout, so you can read it and keep it: #2.
  • Only the proxy, with cargo owning the versions: #3.
  • You are changing the code, so a release build of your own: #4.
  • The first two need no Rust; the last two need Rust 1.88+.
THE TRANSCRIPT // ROUTE BY ROUTE

Four installs, one at a time

Each card below is self-contained: the commands, what they leave on disk, what makes them fail, and the one check that says the install is live.

#1 // PLUGIN CATALOG (RECOMMENDED)

Plugin catalog install

5 STEPS
$ hermes plugins install aphrodite
$ hermes plugins enable aphrodite // or answer yes at the Enable now? prompt
$ cd ~/.hermes/plugins/aphrodite
$ bash download.sh // or: pwsh ./download.ps1 - still required
$ hermes

The catalog is the only lane with no git and no Rust in it: one install, one enable, one download.

OUTCOME // CATALOG INSTALL:

Reviewed pinned checkout of the catalog entry, binaries fetched + SHA-256 verified, plugin enabled.

THE CATALOG RULE

The catalog entry is reviewed and pinned - hermes plugins install checks out exactly that commit, never a branch tip.

Do NOT run aphrodite setup in a catalog-managed directory - still run download.sh (or download.ps1 on Windows) from the installed plugin folder.

SRC: the Hermes plugin guide - Installing from the catalog.

WHAT IT WRITES

The catalog checkout only - plugin.yaml plus the __init__.py shim, in ~/.hermes/plugins/aphrodite. download.sh then fetches the binary and the dylib into ~/.hermes/aphrodite/binaries/, never into the plugin directory, validated against the in-tree SHA256SUMS.txt and magic-byte checked.

WHAT IT FAILS ON

No route to GitHub Releases: the fetch step fails and the plugin stays disabled - register() never downloads anything on its own.

A checksum that does not match SHA256SUMS.txt: the verify step fails, and the honest fix is a re-run, not a hand-copied file.

aphrodite setup run against the catalog directory: it rewrites the loader the catalog manages. Use download.sh from that folder instead.

VERIFY IT WORKS

Start hermes.

The plugin should log that Aphrodite is enabled.

If the binaries are missing, it logs the setup command and stays disabled until you run it.

#2 // GIT CLONE (RECOMMENDED)

Clone, link, download, enable

7 STEPS
$ git clone https://github.com/PlayForm/Aphrodite-Hermes.git
$ cd Aphrodite-Hermes
$ ln -s "$(pwd)" ~/.hermes/plugins/aphrodite
$ bash download.sh // or: pwsh ./download.ps1 (Windows)
$ cd ..
$ hermes plugins enable aphrodite
$ hermes

Pin both explicitly: bash download.sh 1.6.5 x86_64-unknown-linux-gnu. register() never downloads - the only escape hatch is APHRODITE_AUTO_DOWNLOAD=1, which runs the script itself before launching.

OUTCOME // VERIFIED INSTALL:

Binary + native library (dylib) fetched from GitHub Releases, SHA-256 verified, plugin enabled.

WHAT IT WRITES

download.sh resolves the version from the bundled BINARY_VERSION, the monorepo's own Cargo.toml, or the latest published release, detects your platform, and installs aphrodite + libaphrodite_hermes into ~/.hermes/aphrodite/binaries/. Nothing is written inside the plugin tree.

WHAT IT FAILS ON

ln -s onto an existing ~/.hermes/plugins/aphrodite directory: the link lands inside it instead of replacing it. Remove the directory first.

A download.sh run from outside the clone: the script is a file in the tree, so cd into it before running it.

Native Windows PowerShell: bash download.sh needs Git Bash, WSL or MSYS - use pwsh ./download.ps1 instead.

hermes plugins enable aphrodite skipped: enabling is a separate write to Hermes's own config.yaml, so a finished download alone does not register the hooks.

VERIFY IT WORKS

Start hermes.

The plugin should log that Aphrodite is enabled.

If the binaries are missing, it logs the setup command and stays disabled until you run it.

#3 // CARGO

Crates.io install

3 STEPS
$ cargo install aphrodite // proxy binary
$ cargo install aphrodite-hermes // dylib + helper bin
$ aphrodite setup
// cargo installs the binaries only - aphrodite setup then writes a minimal
// loader into ~/.hermes/plugins/aphrodite. For the full plugin, use Option 1
// or 2. Needs Rust 1.88+ (the repo toolchain pins nightly).

Setup ends by starting the proxy - pass --no-launch to skip that, and --force to rewrite an existing aphrodite.toml.

OUTCOME // BINARIES + LOADER:

The proxy binary and the dylib installed by cargo, the runtime home provisioned by aphrodite setup, a hooks-only loader written, the plugin registered.

WHAT IT WRITES

aphrodite setup provisions ~/.hermes/aphrodite/ - the binary, the dylibs, aphrodite.toml from the embedded template (only if none exists, unless --force) and the BINARY_VERSION pin - then writes the hooks-only loader, plugin.yaml + __init__.py, into ~/.hermes/plugins/aphrodite/, removing a stale symlink from older installs first. It ends by running hermes plugins enable aphrodite.

WHAT IT FAILS ON

No hermes on PATH: step one runs hermes --version and fails fast with a clear error, before anything is written.

A missing libaphrodite_hermes aborts setup; a missing core libaphrodite only warns - the plugin loads the Hermes dylib, not the core one.

An existing aphrodite.toml is left alone unless you pass --force; --cache-port and --token-port move the pair off 9797/9798 for a second agent on the same machine.

A failed hermes plugins enable: setup prints a warning and carries on - the binaries are installed, the registration is not.

VERIFY IT WORKS

Option 3 does not install the plugin by itself - after aphrodite setup writes the loader, start hermes.

The plugin should log that Aphrodite is enabled; if the binaries are missing, it logs the setup command and stays disabled until you run it.

MACOS GATEKEEPER

Every artifact copy in aphrodite setup goes through one Gatekeeper-safe path: ditto (metadata-preserving), falling back to fs::copy + xattr -c to clear quarantine, then install_name_tool -id @rpath/<name> and an explicit ad-hoc codesign -f -s - for dylibs. A machine missing Xcode Command Line Tools used to get a SIGKILLed binary with zero diagnostic; every step now prints a specific warning instead.

#4 // FROM SOURCE

Build it yourself

4 STEPS
$ git clone https://github.com/PlayForm/Aphrodite.git
$ cd Aphrodite
$ git submodule update --init --recursive
$ cargo build --release -p aphrodite -p aphrodite-hermes
// needs Rust 1.88+ (the repo toolchain pins nightly). The build outputs land
// in target/release/ - point APHRODITE_BINARY_PATH / APHRODITE_HERMES_DYLIB_PATH
// at them, or copy them into ~/.hermes/aphrodite/binaries/.
OUTCOME // A LOCAL BUILD:

A release build in target/release/ that you point the plugin at, or copy into the runtime home's binaries/ - no installer script, no download.

WHAT IT WRITES

Nothing outside your checkout: cargo build --release writes target/release/aphrodite and target/release/libaphrodite_hermes.dylib (.so on Linux). The plugin reads APHRODITE_BINARY_PATH / APHRODITE_HERMES_DYLIB_PATH, or you copy the pair into ~/.hermes/aphrodite/binaries/.

WHAT IT FAILS ON

A skipped git submodule update --init --recursive: vendored dependencies live in submodules and the build stops early.

A stable toolchain against a repo pinned to nightly: the workspace needs Rust 1.88+ and the repo's toolchain pins nightly.

Build output left in target/release/ while the plugin looks in ~/.hermes/aphrodite/binaries/: set the two env paths, or copy the files across.

Nothing self-heals: the plugin never downloads and never repairs an install, and layout_check.py is report-only.

VERIFY IT WORKS

Start hermes.

The plugin should log that Aphrodite is enabled.

If the binaries are missing, it logs the setup command and stays disabled until you run it.

Every route above converges on the same two directories - what changes on disk.

AFTER ANY ROUTE // THE LAYOUT

What changes on disk

All four routes converge on the same two directories. Nothing else moves: no PATH edit, no shell profile, no system-wide install.

~/.hermes/
├── plugins/
│   └── aphrodite/          ← hooks-only: plugin.yaml + __init__.py loader
└── aphrodite/              ← canonical runtime home
    ├── aphrodite.toml      ← proxy/engine config (written by aphrodite setup)
    ├── BINARY_VERSION      ← binary version pin
    ├── binaries/
    │   ├── aphrodite       ← proxy binary
    │   └── libaphrodite_hermes.dylib   ← dylib the plugin loads
    ├── ccr.db              ← SQLite CCR store (created on first run)
    ├── directives/         ← active directive files
    └── logs/               ← proxy/engine logs
THE PLUGIN DIRECTORY

The plugin directory stays hooks-only: it carries just plugin.yaml and the __init__.py loader that registers hooks and tools, and the plugin never writes, downloads or modifies anything inside it.

THE RUNTIME HOME

Every runtime artifact lives in ~/.hermes/aphrodite/: binaries, config, directives, the CCR database and logs. That split is what lets the catalog own the checkout while the binaries live somewhere else entirely.

On plugin startup layout_check.py checks toward this schema; installed layouts are already canonical, because aphrodite setup produced them.

8 STEPS WHAT APHRODITE SETUP DOES, IN ORDER OPEN + CLOSE −
  1. Verifies hermes is on PATH (hermes --version) - fails fast with a clear error if not.
  2. Creates the runtime home: ~/.hermes/aphrodite/ and ~/.hermes/aphrodite/binaries/.
  3. Copies the binary into binaries/ with locked-down permissions - macOS copies go through the Gatekeeper-safe path above.
  4. Locates libaphrodite_hermes (and the optional core libaphrodite): local build and install dirs first, then the matching GitHub release with SHA-256 verification. A missing libaphrodite_hermes aborts setup; a missing core dylib only warns.
  5. Writes aphrodite.toml from an embedded template (--cache-port / --token-port, defaults 9797/9798) - only if none exists, unless you pass --force.
  6. Writes the hooks-only loader into ~/.hermes/plugins/aphrodite/: plugin.yaml + the __init__.py shim, always refreshed on re-run; a stale symlink from older installs is removed first.
  7. Writes the BINARY_VERSION pin into the runtime home.
  8. Runs hermes plugins enable aphrodite - a failed registration prints a warning, it does not abort.
REVERSE UNINSTALL // THREE COMMANDS AND A DIRECTORY OPEN + CLOSE −

Disable the plugin, remove the loader, then stop anything still running:

hermes plugins disable aphrodite
rm -rf ~/.hermes/plugins/aphrodite
pkill -f "aphrodite" 2>/dev/null || true

Remove ~/.hermes/aphrodite/ as well to clean up the binaries, config, CCR database and logs the download scripts or aphrodite setup wrote.

PROXY // THE STANDALONE LANE

Run it without Hermes

The same compression engine runs as a standalone proxy: point any OpenAI-compatible client's base_url at http://localhost:9798 (token) or :9797 (cache), and responses compress over plain HTTP.

Invoked without an aphrodite.toml, the binary needs --api-key or APHRODITE_API_KEY. That is a startup requirement, not an upstream call - a placeholder is enough to prove the binary serves.

PORTMODEWHAT IT SERVES
9797cachethe cache proxy - threshold 2048 bytes by default
9798tokenthe token proxy - threshold 256 bytes by default
$ ./aphrodite --api-key «redacted:sk-...» --listen 127.0.0.1:9798
$ curl http://127.0.0.1:9798/health
{"status":"healthy","ccr":true,"mode":"token","version":"<current version>","fill_pct":...}
aphrodite: no API key configured - set APHRODITE_API_KEY env var or api_key in aphrodite.toml STDERR
No aphrodite.toml in the working directory - the CLI mode has no config to read a key from, so the flag (or the env var) is the whole requirement.
REVEALED

You do not need a real Hermes session, a real Hermes install or a real upstream API key to confirm the binary itself works: starting the proxy and hitting /health never calls upstream. Set APHRODITE_NO_AUTO_LAUNCH=1 if you launch it yourself and do not want the plugin to start a second pair - there is no auto_start key in either config file.

The full surface is documented on the proxy pages: architecture, compression, handlers, retry.

/CONFIG.TOML

Configuration

Two files matter and they share no keys: aphrodite.toml for everything that tunes how Aphrodite compresses, and Hermes's own config.yaml for enabling the plugin.

# resolution order:
./aphrodite.toml then ~/.hermes/aphrodite/aphrodite.toml
# precedence:
env var > TOML > default

[compression]
auto_reload = false # opt-in

[flow]
budget_chars = 2600 # hard cap per turn
TEMPLATES IN THE REPO: aphrodite.toml.example + the embedded template

Two shipped files stay in sync: aphrodite.toml.example (the annotated reference) and the embedded template the binary ships with.

Keys not yet wired into the runtime are annotated DOCUMENTED BUT UNWIRED in the example - it is the source of truth for the documented surface.

TWO PARSERS, ONE FILE

The Rust HTTP proxy (config/proxy.rs) reads [[proxies]], [defaults], the four hot-reload thresholds plus auto_expand / auto_expand_limit / max_request_body_size, and preview_max_chars. The Hermes dylib session (config_loader.rs) reads the [compression] engine keys, [defaults] model/api_url, [flow], [directives], [prompts] and [templates].

NOT HERMES'S CONFIG.YAML

The only Aphrodite-relevant keys in config.yaml are plugins.enabled: [aphrodite], added by hermes plugins enable, and optionally context.engine: aphrodite with its threshold. Ports, thresholds, preview style and prompt wording all belong in the toml.

Every knob the file exposes is explorable on /config/, and the complete schema is /docs/config/aphrodite-toml/.

FAILURES // WHAT THE MESSAGE MEANS

When it does not come up

Every install failure on this page announces itself in one of six ways. The proxy's own stderr goes to ~/.hermes/aphrodite/proxy-stderr.log - read that file before anything else.

SYMPTOMCAUSEFIX
the plugin logs the setup command and stays disabledbinaries missing from ~/.hermes/aphrodite/binaries/bash download.sh (or pwsh ./download.ps1) in the plugin folder
download.sh stops at the verify stepchecksum does not match SHA256SUMS.txtre-run the script; check network access to GitHub Releases
no API key configuredno aphrodite.toml in the working directory--api-key or APHRODITE_API_KEY
port already in useanother proxy already bound to 9797/9798tail proxy-stderr.log; APHRODITE_CACHE_PORT / APHRODITE_TOKEN_PORT
the binary is SIGKILLed on launch (macOS)quarantine, or no Xcode Command Line Toolsre-run aphrodite setup - ditto, xattr -c, ad-hoc codesign
a health-poll warning after launcha port did not answer within 5 secondsthe warning names the port; check proxy-stderr.log

Before launching, the plugin probes both ports' /health endpoints and skips the launch when another process already answers a confirmed Aphrodite health body - so a second Hermes session does not start a second proxy pair. A failed registration is a warning, never an abort.
