HERMES // THE INTEGRATION

Living inside Hermes

Aphrodite connects to Hermes Agent as a native plugin, not as a proxy you point a client at. It is the reason the interception lives inside the turn: tool output never hits a wire, so only hook-level registration can catch it before it becomes message history - six hooks, thirteen tools, and an optional context engine, every call forwarded into the Rust dylib. Two proxy processes still run alongside as subprocesses, and a canonical runtime home under ~/.hermes/aphrodite/ holds the binaries, config, CCR database, directives, and logs.

HERMES ALONE - nothing stands between a tool and the model.

Every file read, build log, and JSON blob enters the message history raw, because nothing intercepts it - the agent spends its token budget reading noise instead of reasoning.

That is the baseline cost the other two configurations exist to remove.

HERMES + APHRODITE - the plugin lane intercepts output before it becomes message history.

The hooks classify, store, and replace raw output with a type-aware marker of ~15 tokens instead of hundreds, the agent retrieves the full content only when it actually needs it, and the injection assembler adds directives, nudges, and the recall catalog to every turn under a hard byte budget.

Measured over 200 real Hermes sessions: 26.9% of all context tokens deflected, a median session saved ratio of 22.9%, and ~22,921 tokens saved per API call.

THE TRADE-OFF IS STATED PLAINLY: the hooks are Hermes' contract - no other client can register them, so this lane works with Hermes only.

HERMES + APHRODITE + THE PROXY - the plugin already spawns both listeners, so the third configuration is running without extra setup: point base_url at :9798 and any OpenAI-compatible client gets the same CCR compression over plain HTTP.

That is the agent-to-agent path - a second agent, a script, or an external tool can converse through the same compressed channel, share the persistent SQLite store (which survives a restart; the plugin lane's inline store is session-scoped), and call the tool relay to retrieve or create CCR entries.

THE LIMIT IS REAL TOO: the proxy only sees HTTP traffic - no tool-output interception, no terminal compression, no directives, no context engine, and SSE streams pass through uncompressed.

Because of that the proxy extends the stack to other callers; it does not replace the hooks inside Hermes.

LIFECYCLE // SESSION TO SESSION

What happens when you launch Hermes

hermes starts
→ plugin loads · dylib resolved once per process, smoke-tested in a subprocess
→ a faulting image degrades to "plugin disabled" instead of killing the gateway
→ two proxies spawn - a healthy pair is reused, never duplicated
→ on_session_start resets all per-session state
→ turn loop: pre_tool_call → transforms → pre_llm_call → post_llm_call
→ session ends · markers do not survive a restart - a new session starts a fresh store

THE DUAL PROXIES: TOKEN ON :9798 (SQLITE, PERSISTENT, COMPRESSES ABOVE 1 KB) AND CACHE ON :9797 (IN-MEMORY, COMPRESSES ABOVE 8 KB). NO HOT-RELOAD - RESTART THE SESSION TO PICK UP A NEW BUILD. SRC: README.md:298-299; docs/guides/hermes-integration.md:107-108.

OPT-IN // CONTEXT ENGINE

The optional third integration point

Enable with APHRODITE_CONTEXT_ENGINE=1. It is non-destructive by design - the engine's should_compress always returns False, deferring to Hermes' own threshold accounting while the proxy and hooks do the heavy lifting.

engine_threshold_pct 45 # compress at % context fill
engine_protect_first 2 # messages kept at the start
engine_protect_last 5 # messages kept at the end
engine_min_msgs 8 # minimum messages before activating
