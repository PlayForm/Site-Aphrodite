CRATES // WORKSPACE MANIFEST

Crates

A tool call's output becomes part of the model's context, and one crate in this workspace is the code that transforms it before the model reads it.

Two workspace crates plus the vendored Headroom fork that carries the content transforms.

It is the reason the fork stays separate: Aphrodite adds the preview pipeline, CCR storage, Hermes integration, and dual-proxy architecture on top of Headroom, instead of rewriting the transforms.

The binary links the fork's headroom-core library only, published as aphrodite-headroom-core v0.2.1: upstream's proxy surface does not ship in Aphrodite.

Every crate is installable on its own; which one an install actually needs follows from the dependency chain.

01 // WORKSPACE // 3 PUBLISHED NAMES

What the workspace publishes

3 names leave this workspace, and none of them is typed by hand: the workspace Cargo.toml decides which crates exist, and every entry is read from that crate's own manifest - its name, its version, its description. A crate added to the workspace appears in the roster with no edit anywhere, and a crate removed from it leaves the same way.

02 // CASES // THE MANIFEST, CRATE BY CRATE

Each crate in full

Each name declares itself once, in its own manifest: the version is that file's version and the role is that file's description, so the roster cannot drift from the crates it describes. What each one puts on disk is the difference that matters before an install - a cargo install for the two workspace crates, and for the vendored fork the dependency line that pulls it in, because a library has no binary to place. Colour is the crate's kind and not its rank: canary is a workspace crate a reader installs, teal is the vendored fork that arrives as a dependency.

03 // DEPENDENCY // ONE CHAIN, 3 LINKS

Who pulls whom

The three names are one chain and not three islands. Each link is a path dependency in the manifest one step up, so the direction never reverses: the vendored core knows nothing about the proxy, the proxy knows nothing about Hermes, and Hermes is the only crate that speaks to the agent. That is why an install names two crates and receives three.

DEPENDENCY

WHAT A CARGO INSTALL PULLS // DECLARED IN EACH MANIFEST

aphrodite-hermes v1.8.1
Installed directly. Its manifest declares aphrodite as a path dependency at the same version, so building this crate builds the proxy crate with it.
aphrodite v1.8.1
Installed directly. Its manifest declares the vendored fork's core library as a dependency under its published name, so the transforms are compiled into the binary rather than reimplemented beside it.
aphrodite-headroom-core v0.2.1
Never installed directly: it arrives as aphrodite's dependency, as a library only. Upstream's proxy surface does not ship in Aphrodite.

The first two are the ones a user installs; the third arrives as their dependency.

The chain is also why the fork stays separate rather than being absorbed: the vendored core carries the content transforms and nothing else, the proxy adds the preview pipeline, the CCR store, the tool relay and the dual-proxy architecture around it, and Hermes adds the tool schemas, the hook dispatch and the skill registration on top of the proxy. Each layer stays installable, testable and replaceable on its own, and the boundary between them is a manifest line rather than a convention.

04 // CONFIGURATION SURFACE // APHRODITE.TOML.EXAMPLE

What the crates read at runtime

One TOML file is read by both halves of the pair: the proxy takes its listeners and its flow budget from it, the dylib takes the compression thresholds and the previews. The shipped example carries the keys grouped the way the file groups them, and every value is the example's own default rather than a recommendation.

PROXY // PROXIES, DEFAULTS, FLOW

[[proxies]]
cache → 127.0.0.1:9797 timeout 120
token → 127.0.0.1:9798 timeout 300
tool_relay = true (both)
[defaults]
api_url = "https://api.openai.com"
ccr_ttl_seconds = 3600
[flow]
budget_chars = 2600

ENGINE // COMPRESSION, PREVIEWS

[compression]
engine_threshold_pct = 30
tool_threshold_token = 256
tool_threshold_cache = 2048
terminal_threshold = 256
inline_threshold = 1024
code_multiplier = 1.0
auto_reload = true # shipped default
[previews]
preview_max_chars = 0

Keys without a live consumer are annotated DOCUMENTED BUT UNWIRED in the example; the [templates.*] section is live configuration - preview families, the marker block, prompt templates and the reverse key map render from these format strings (hardcoded builders apply when a block is absent).

Marker grammar: <<<CCR:hash|type|size>>>
