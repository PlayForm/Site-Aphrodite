SHOWCASE // THE PLUGIN IN ACTION

The plugin, worked

A tool call's output is appended to the model's context, and the model reads every line of it. These are the entries where Aphrodite decides what arrives instead.

Anonymized throughout - no names, no secrets, no real sessions; every entry is a real behavior of the pipeline dressed in generic content.

HOW THESE EXAMPLES WERE PRODUCED provenance · what the corpus lines are checked against · the four labels OPEN + CLOSE −

Every example is a real behavior of the pipeline dressed in generic content: what the agent sends (the raw stream), what it sees back (the enriched preview), how the bytes come home (the retrieval round-trip), and why the thresholds made that decision.

All previews marked as corpus lines are byte-identical to the docs catalog; the rest are faithful fragments.

That catalog is the enriched-preview table in docs/proxy/compression.md together with the preview-form table in the repository README - both are public, so every corpus line can be checked against them, character for character.

Anonymized throughout - no names, no secrets, no real sessions.

THE FOUR PROVENANCE LABELS

"Anonymized" and "illustrative" are not the same claim, so every entry names its own provenance in text beside its title. Colour reinforces the label; it never carries the distinction on its own.

  • Catalog-exact - the preview line is byte-identical to the documented enriched-preview catalog, so it can be checked character for character.
  • Illustrative - authored: a faithful fragment of the shape with varied generic numbers, not a capture and not a catalog line.
  • Captured - recorded from a real run and then anonymized. No entry claims it today; the label exists so a real capture can be published without being called illustrative.
  • Engine-verified - checked against a named engine version, so the behavior is pinned to a release rather than to a reading of the code.

THE FOUR OUTCOMES

An example says how its bytes reached the transcript, because four different mechanisms that render identically are four mechanisms a reader cannot tell apart. The counts are read off the bank.

  • Compressed · 16 - the output crossed the surface's threshold: hashed, stored, and replaced by a preview line plus a marker.
  • Passed through · 2 - under the threshold, or stopped by a skip gate: the bytes reach the transcript unchanged and nothing is stored.
  • Injected · 1 - never a tool result: behavioural text assembled in a fixed order and placed into the prompt.
  • Callback · 1 - a relay call that answers immediately and delivers the real result later, at a callback URL.

THE CONTEXT ENGINE // WHAT IT DOES NOT DO

Compress returns the transcript unchanged

The registered engine is opt-in (APHRODITE_CONTEXT_ENGINE=1; the TOML key defaults true) and requires Hermes >= 0.20.2 - the first release with pre_tool_call modify.

What it does: records token usage from each response.

What it never does: should_compress always returns false (it defers to Hermes' own accounting), and compress returns the transcript unchanged - non-destructive, because the transform hooks already shrank the tool output.

It never forces a compaction, never rewrites messages, and never touches the inline store.

SRC: docs/plugin/context-engine.md:38-48
THE PREFETCH REFUSAL // v1.6.6

Some paths are never read

aphrodite_prefetch would happily warm the store from any path - so the guard names the paths that must never be read and refuses them outright:

WHAT THE AGENT ASKS FOR
.env
auth.json
~/.ssh
the Hermes home
any non-file path
WHAT THE SYSTEM RETURNS
ReadOutcome::Refused
refuse_reason: "..."

the file is not opened, not hashed,
not stored - the prefetch returns
a refusal instead of the content

The same release hardened setup the same way: the Hermes-home plugin directory is report-only - no symlink removal, no writes, no deletes - and the dylib arm refuses installs when the in-tree checksums are missing.
