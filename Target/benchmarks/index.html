METHOD // ONE PAYLOAD, COUNTED TWICE

How a ratio is computed

A ratio on this page is one payload counted twice: the tokens the tool produced, the tokens the model actually reads, and the first divided by the second.

Nothing else enters the number - no weighting, no projection, no averaging across calls.

The denominator is not the raw output minus a preview.

It is the whole replacement the model receives: the marker, its type, its size, and the short preview that lets the model decide whether the bytes are worth retrieving.

STEPWHAT IS COUNTEDWHERE IT COMES FROM
BEFOREthe payload as the tool produced it, in tokensthe corpus sample
AFTERthe marker plus its preview, in tokensthe compressed sample
▲ RATIObefore ÷ after, reported as a whole multiple▲ the two counts above

The corpus is fixed, and it is the same corpus for every row: the per-type table takes one representative sample per output class, and the headline figure aggregates the whole set - 106 KB in, 800 B out, 132× overall, with the single best document reaching 610×.

Timing is reported on a different axis on purpose.

Classification is 40-123 ns and is timed on its own because it runs on every call.

The whole compress step is sub-millisecond.

8-40 ms is what a client waits once the HTTP round-trip is included.

And the ~10 ms headline sits near the fast end of that band.

TWO HALVES // TWO CONFIDENCE LEVELS

What is measured and what is estimated

The page has two halves and they do not carry the same confidence.

Everything in the plates and the per-type chart is measured: a fixed payload goes in, a marker comes out, and the quotient is arithmetic.

The session study is an estimate by construction: it reconstructs what each API call would have carried with every marker expanded, so its figure depends on the tokenizer used to count that reconstruction.

That is why it ships as a band with a stated sensitivity range rather than as a single percentage.

Neither half is a vendor number.

A reader with a checkout can re-derive the measured half exactly and the estimated half to within its band - the harness section below is the first half of that sentence, and the case study is where the second half is argued.

BUILD OUTPUT 140×

GIT DIFF 23×

TERMINAL 20×

shell output - listings, test runners, the progress lines that carry no verdict

The bars are drawn at the ratios' log-scale positions, so the top row sits at full width and each row below it reads as a step down.

The chart peaks at 416×, on the browser snapshot: a serialised DOM repeats the same wrapper nesting down to the leaves, and the ratio is a measure of exactly that repetition.

The 610× plate is deliberately outside this chart.

It is not a sixth class: it is the best case on a single long low-entropy document, while the 5 rows above are one representative sample per class and 132× is the whole corpus counted at once.

Plotting a best case beside five class samples would invite a comparison the number cannot support.

Read the chart as a ranking, not a promise: a diff, a build log and a terminal session are the ordinary material of an agent turn, and they land between 20× and 140×, while the median the README reports for the same table is 23×.

the smallest row, TERMINAL at 20×, is still a fifth of the tokens SUPPRESSED
20× - the floor of the chart, and the floor is the useful number: a terminal dump that compresses 20× is a dump the model can afford to keep.

REAL-WORLD STUDY // 200 SESSIONS

What 200 sessions measured

The study takes 200 real Hermes sessions - 6,843 API calls over three days - and reconstructs every call's payload from the session transcript.

Each payload is counted twice: as the model saw it, with the CCR markers in place, and with every marker expanded back to the content it replaced, which is what stock Hermes would have sent.

The difference between those two counts is the saving.

Nothing is simulated in that arithmetic - the markers, the retrieval calls and the expansions are the ones the transcripts contain - but the expansion depends on a tokenizer, so the result is a band rather than a point.

THE SHAPE OF A SESSION // FOUR PAYOFFS

Why the same engine reports four numbers

Savings track tool-output volume, not session count.

A chat-only session has nothing to compress, so it saves ~0%.

A light developer session saves ~5%.

A tool-heavy session lands in the 20-25% band.

And a simulated pure-tool loop - a diff, an ls, a build and a search on repeat - reaches 76-82%.

That last figure is a stress test, not real usage, and the bars above label it as one.

The 183 / 200 row is the other way to read the same data: in 183 of the 200 sessions something was saved.

The two rates beside it answer different questions - 22.9% is the median session's saved ratio, 22,921 is what an average call did not have to carry - and both are reported because neither alone describes the study.

The retrieval tax is the cost side of the ledger: 2,275 retrieve calls returned 2,011,583 tokens, roughly 1.3% of what was saved.

Savings are gross; this row is what the model paid to get its bytes back.

PROVENANCE // WHERE THESE NUMBERS COME FROM

Nothing on this page is typed

Every figure above is extracted from the repository on the build that produced this page - not copied into a template once and trusted afterwards.

The generator reads the README and the docs tree, writes the numbers into a generated record, and the page renders that record. A figure the repository stops carrying stops the build; it never survives as a stale plate.

The table below is the whole chain: the fact, the file it is read from, and the part of this page it feeds.

FACTREAD FROMWHAT IT FEEDS

A wrong figure is fixed in the repository and the pin advances - never in the generated record, which the next build overwrites.

That is what makes the SRC line under each plate an address rather than a formality: the line numbers beside it come from the same pass that produced the number above it.

FIVE EXAMPLES // WHAT EACH ONE PROVES

What a run actually does

Each example starts its own proxies, drives them over HTTP, and exits non-zero the moment a promise breaks - so a green run is a verdict, not a printout.

01 bench_01_corpus - the standard corpus, end to end OPEN + CLOSE −
Spawns the cache and token proxies on benchmark ports, pushes one sample per content type through /ccr/create, retrieves each one through /retrieve, then prints the per-label table. Exits non-zero on any retrieve miss, so a ratio it prints is a ratio that survived the round-trip.
02 bench_02_threshold - the size boundaries OPEN + CLOSE −
Sweeps /ccr/create and /retrieve across the threshold-adjacent sizes - the inline zone, then 1 KB, 4 KB and 8 KB - in both cache and token mode. Content is always stored, a hash is always returned, and the stored bytes come back byte-for-byte; a boundary violation exits non-zero.
03 bench_03_retrieve - retrieval correctness OPEN + CLOSE −
Ten labelled cases: same-port retrieve in both modes, cross-port isolation in both directions, the inline zone, UTF-8 content retrieved byte-for-byte, a fifty-insert storm with no misses, deletion, and a double store of the same content. This is the example that proves a marker is a promise and not a summary.
04 bench_04_ema - the auto-tune loop OPEN + CLOSE −
Drives the compression-ratio EMA through three phases: ten highly repetitive payloads, then ten near-incompressible ones, then ten more repetitive ones. The EMA must climb, decay, and partially recover - and the per-type threshold multipliers must not flip a linter or build-output sample to the wrong half.
05 bench_05_type_coverage - one sample per class OPEN + CLOSE −
Pushes one representative sample per content type through a token-mode proxy and reports each type's ratio plus the classifier's verdict. Build, diff, git, gitlog, ls, test, grep, Rust, Python, Go, JavaScript, JSON, error, log, linter and plain text: a type that fails to compress, or whose retrieve round-trip misses, exits non-zero.

LIMITS // WHAT THE NUMBERS ARE NOT

Where the figures stop

NOT A TYPICAL CASE

610× is the ceiling on one long low-entropy document. The per-type chart peaks at 416×, and the median the same table reports is 23× - quote the ceiling only with the corpus attached.

NOT A SINGLE PERCENTAGE

The session saving is a band, not a point: ~24-33% across a 3.0-4.5 chars/token sensitivity range, centered ~27%. Any single number inside that band is a reading of the same data, not a better measurement.

NOT REAL USAGE

The 76-82% pure-tool figure comes from a simulated diff+ls+build+search loop. It is a stress test of the engine, and the real sessions it sits beside saved 20-25% when they were tool-heavy.

NOT NET OF RETRIEVAL

Savings are counted before retrieval. The study's own tax row - 2,275 calls, 2,011,583 tokens - is what the model spent getting bytes back, roughly 1.3% of the tokens saved.

None of this weakens the claim the page makes.

A compression proxy earns its place on the ordinary turn - a diff, a build log, a terminal dump - where the ratio is 20× to 140× and the model keeps working from the preview.

The ceiling is what the engine can do; the median is what a session gets.

If a number here disagrees with your own run, the harness is the arbiter: the examples ship with the crate, and the SRC lines above name the README section each figure is copied from.
