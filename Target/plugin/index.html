PLUGIN // THE THIN LOADER

The plugin

Aphrodite ships as a Hermes Agent plugin: a thin Python registration shim over a Rust dylib. Six hooks, thirteen tools, and an opt-in context engine - all declared in plugin.yaml, all logic living in libaphrodite_hermes.dylib. This page documents the v2.2.6 plugin spec.

v2.2.6 STANDALONE 6 HOOKS 13 TOOLS ZERO LOGIC IN PYTHON
plugin.yaml // THE DECLARED SURFACE

What the manifest declares

name: aphrodite
version: 2.2.6
kind: standalone
requires_hermes: >=0.20.2
requires_hooks: true
provides_context_engine: true
# provides_hooks (6)
on_session_start · pre_tool_call
transform_tool_result · transform_terminal_output
pre_llm_call · post_llm_call
# provides_tools (13)
retrieve · compress · stats · rebuild · files · diff
search · directive · test · catalog
reclassify · prefetch · prefetch_status

ENGINE THRESHOLD SEMANTICS: -1 = ALWAYS COMPRESS · 0 = DISABLED · >0 = FILL PERCENT. SKILLS ARE NOT SHIPPED WITH THE PLUGIN - THEY LIVE DEV-SIDE.

ARCHITECTURE // CALL CHAIN

A thin shim, a Rust brain

Hermes Agent (hooks + tool dispatch)
│
__init__.py - ctypes FFI, registers hooks/tools/engine · no logic
│
libaphrodite_hermes.dylib - Hermes bridge (JSON contract) · 6 hooks · 13 tools · schemas
│
libaphrodite (core engine) - ALL compression logic: hooks · resolve · retrieve · marker · preview · directives
│
CCR store - SQLite :9798 / in-memory :9797 / inline

Registration is driven by the dylib: the shim asks the dylib for its hook names and tool schemas and registers one callback per name. It is the reason there is no hot-reload: the dylib is resolved once per process, so to pick up a new build you restart the Hermes session.

DOWNLOAD // EXPLICIT STEPS ONLY

register() never downloads

Binaries are never shipped in the repository. Fetching them is an explicit setup step you run yourself - and the verification is mandatory, not best-effort:

  • SHA-256 against the in-tree checksum list - SHA256SUMS.txt, generated by CI into the tree; a mismatch is refused outright.
  • Magic-byte validation - the downloaded file must be a real ELF / Mach-O / PE image, or it is rejected.
  • Backup + restore - an existing install is backed up and restored if any step fails. No release-hosted fallback.
  • A missing binary disables, not breaks - the plugin logs the setup command and stays disabled until the binaries are present.
$ git clone https://github.com/PlayForm/Aphrodite-Hermes.git
$ cd Aphrodite-Hermes
$ ln -s "$(pwd)" ~/.hermes/plugins/aphrodite
$ bash download.sh // or: pwsh ./download.ps1
$ cd ..
$ hermes plugins enable aphrodite
$ hermes
COPY THE FULL SEQUENCE:

ALSO ON THE STORE: the plugin is in the Hermes plugin catalog - the reviewed, pinned alternative to the manual clone above. hermes plugins install aphrodite checks out the catalog entry's exact commit, then bash download.sh from ~/.hermes/plugins/aphrodite still fetches the binaries (never aphrodite setup against the catalog-managed directory). The full flow is on SETUP; the mechanics are in the Hermes plugin guide.

LLM API KEY REQUIRED: the proxy is an OpenAI-compatible forwarder and needs its own credentials - APHRODITE_API_KEY, aphrodite setup, or api_key in ~/.hermes/aphrodite/aphrodite.toml. Hermes' provider config is NOT reused, and there is no keyless mode: without a key the proxy refuses to start.

FILESYSTEM // CANONICAL LAYOUT

What changes after install

~/.hermes/
├── plugins/aphrodite ← manual symlink to the plugin repo
└── aphrodite/ ← runtime home
├── binaries/aphrodite ← proxy binary, fetched + verified
├── binaries/libaphrodite_hermes.dylib
├── aphrodite.toml ← config
├── directives/ ← 7 built-ins materialized
├── ccr.db ← SQLite CCR store
└── proxy-stderr.log ← proxy logs (empty = healthy)

The runtime home self-heals toward layout_schema.json at startup: misplaced config and binaries are moved to their canonical paths, and stale plugin-source copies are quarantined. It is the reason the self-healing stops at the Hermes-owned boundary: the ~/.hermes/plugins/aphrodite install dir is Hermes' territory, and the plugin never creates, converts, or modifies it.

EVOLUTION // HOW THE SURFACE GREW

The six hooks, the version pairing, and the 14-to-13 correction

on_session_start
session starts

resets all per-session state to a clean baseline - injects nothing

pre_tool_call
before a tool executes

auto-backgrounds long-running calls; splits chained commands

transform_tool_result
after every tool call

compresses large tool results into CCR markers

transform_terminal_output
after every terminal execution

compresses large terminal output into CCR markers

pre_llm_call
before each LLM request

injects directives, nudges, and the recall catalog

post_llm_call
after each LLM response

archives the turn, advances the counter, expires stale state

SRC: docs/plugin/hooks.md:13-20 - every hook is a thin dispatch that forwards to the Rust dylib; the dylib holds all the behavior.

THE VERSION PAIRING · BINARY_VERSION MECHANICS
1.6.6 ↔ 2.2.6

Today's pairing: binary 1.6.6, plugin 2.2.6. Every release moves both: "Binary `1.6.5 → 1.6.6`, plugin `2.2.5 → 2.2.6`."

BUMPED LAST

BINARY_VERSION is pinned to a binary release tag the plugin can download. Since the first plugin-first release (v1.4.6), the plugin is tagged before the parent, so the pinned version points at assets that already exist.

OR IT REFUSES

The plugin warns before download.sh when the pinned BINARY_VERSION points at a release with no assets - and since v1.6.5, a checksum mismatch is a hard refusal, not a warning.

SRC: CHANGELOG.md v1.4.6/v1.4.4/v1.6.5/v1.6.6 entries · the Aphrodite/v1.4.6 release note ("released plugin-first ... points at assets that already exist")
13 TOOLS, NOT 14 · THE CORRECTION IS A BEAT

v1.6.5 corrected the manifest: "14 tools" → "13 tools" - the release dylib registers exactly the 13 declared tools. The 14th, aphrodite_debug, is debug_assertions-gated out of release builds, matching what hermes plugins validate enforces. Earlier, v1.6.1 had already removed it from provides_tools, closing the catalog-review mismatch on the pinned tree - and v1.4.6 had done the same for aphrodite_navigate, the navigation tool whose feature was unbuildable. The declared surface and the running surface are kept identical on purpose.
