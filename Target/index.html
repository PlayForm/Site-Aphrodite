Aphrodite

CONTEXT MANAGEMENT FOR TOOL-USING AI AGENTS

Aphrodite keeps noisy tool output out of your agent's context - it turns logs, diffs, files, searches, JSON, and browser snapshots into compact previews the agent can act on, with the original always one retrieval away.

One binary. Zero dependencies. Millions of tokens saved.

610× COMPRESSION Best case, on large low-entropy prose.
132× OVERALL The whole standard corpus: 106 KB to 800 B.
~10MS E2E OVERHEAD Including the HTTP round-trip; the spread is 8-40 ms.
156M+ TOKENS SAVED 200 real sessions, 6,843 API calls, Sep 2026.
THE PAIR // STREAM + PREVIEW

The agent spends its budget reading noise

Every file read, build, code search, or browser open floods the agent's context with raw output - compilation logs, accessibility trees, JSON blobs.

The agent spends its budget reading noise instead of reasoning.

Aphrodite intercepts output before it reaches the LLM and replaces it with a compact, structured preview - because the agent's reasoning budget is the context budget, and raw noise spends both.

The agent sees ~15 tok of metadata instead of hundreds - and retrieves the full content only when it actually needs it.

It is the reason tool-heavy agents keep working: the context window stops paying for noise before the reasoning starts.

The pane below is not a screenshot of that idea. It is a terminal that keeps running: a release build, then a code search, then a directory listing, then a test run, then a JSON body, then back to the build - indefinitely, each at the pace its own tool really prints at. Nothing is scripted to look good; every line is the output that command produces, and the one line on the right is recomputed from those lines as they land.

This pane never stops. Each command runs, settles, and the screen clears for the next one: a build that stalls and then bursts, a search that arrives flat and fast, a listing, a test run that ticks, a JSON body that only parses on its last line. The fade, the dim and the mute are the suppression marks the engine would put on these same lines - repeated compile steps recede, counted warnings mute, the one line that stopped the build stays at full strength.

PREVIEW // WHAT THE MODEL READS
ONE LINE, ONE MARKER build
[build:2E 2W 142L | error[E0432]: unresolved import `crate::noise`]
<<<CCR:a1b2c3d4|build|4565>>>

The right pane is rewritten as the left one prints, and it is never a lie: the counts are the counts of the lines that have actually arrived, and the marker's size is the size of the bytes behind it at that moment. Read it as a sentence - if the stream ended here, this is the line the agent would read - and watch the tally climb to the settled line the build really ends on.

The chip above the result is the classifier's verdict. It changes with the command, because the preview shape changes with it: a build counts errors and warnings, a search counts hits and files, a listing counts entries and extensions, a test run counts passes and failures, and a JSON body counts items and keys. One engine, five arms of it.

The marker is the address of the original bytes.

The agent pays for them only when the preview fails to answer the question.

Watch the left pane print: that is the flood arriving, one line at a time, and every line of it is budget. Watch the right pane while it prints - the counts climb, the marker's size grows, and the whole thing settles on the one line the agent would actually have read. A marker only means something once there is a flood behind it to address, which is why it is drawn from the flood and not beside it.

Five commands, five shapes of answer: the build counts errors, warnings and lines; the search counts hits and files; the listing counts entries and extensions; the test run counts passes and failures; the JSON body counts items and keys. That is one engine reading five kinds of output - the classifier naming the content, and the preview rendering the answer that name earns.

PIPELINE // 4-STAGE ABSORPTION

Four steps, one decision

Every tool result runs the same four steps in the same order, and only one of them costs anything measurable.

The first two are the engine's: name the content, then render the one line that describes it. The third is storage, and it is deliberately boring. The fourth is not the engine's at all - it is the agent's, and it is the only step that spends the budget the other three just saved.

Read the grid left to right, then top to bottom: each card is one step, the figure on it is what that step costs, and the line under the rule is what it decides.
